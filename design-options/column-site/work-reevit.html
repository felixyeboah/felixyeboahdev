Payments that keep working when the provider behind them doesn’t.

The problem

Felix was building the store for Miss Cookie Spices when payments started failing. The provider’s webhook had gone unreliable: sometimes it fired, sometimes total silence.

Switching providers meant rewriting almost the whole integration.

The question

If one client hit this, how many developers were quietly accepting broken payment flows?

Enterprise teams have orchestration layers like Primer. Builders starting from scratch had nothing that simple.

The approach

A universal remote for payments.

  • Integrate once. One snippet, any provider behind it.
  • One shape. Same request and response, so switching never touches business logic.
  • No downtime. Whichever provider is answering takes the charge.

A declined charge isn’t a lost sale.

When a provider declines or stops answering, the same charge moves to the next one in the merchant’s chain, inside the same tap. Nobody has to ask the customer to try again.

Retries that change lanes.

Subscriptions and instalments retry on a schedule, and on a different provider when one keeps declining. The invoice gets paid without anyone chasing it.

No website needed.

A payment link on WhatsApp, a QR on the counter, or the drop-in checkout. Mobile money and cards work on day one.

Every provider, one screen.

Payments, routing decisions, webhooks and provider health in one place, in test and live mode. Workflows can run the moment a payment lands.

Under the hood

  • 01Health-checked routingReal-time provider health checks decide the fallback order, so a charge skips a provider that is already struggling.
  • 02Fraud rules firstMerchant-level rules for country, amount limits and BIN blocklists run before a charge leaves.
  • 03Envelope encryptionMerchant keys are sealed with a data key wrapped by a KMS-managed key, decrypted in memory at call time and never logged.
  • 04Normalised webhooksEvery provider’s events arrive in one shape, so switching providers never rewrites business logic.
